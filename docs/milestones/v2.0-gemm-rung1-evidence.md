## ⚠️ Open question before committing Rung 2: is the 1.11× fused speedup real?
It is internally inconsistent with the 0.06× bare fp16 result: GEMM cost is
O(N³) matmul, fusion only saves an O(N²) round-trip, so a non-tensor-core fused
kernel should NOT beat a cuBLAS-backed fused baseline. Two very different
explanations, needing the artifacts to distinguish:
1. the fused kernel used tensor cores (WMMA) while the bare one didn't → a
   genuine fused+tensor-core win (great), OR
2. the fused baseline was measured against something slow (a baseline artifact,
   like the v1.0 bug) → 1.11× is not real.
**Verify before Rung 2:** inspect `matmul_bias_gelu_fp16` `stage5_polish/.../kernel.cu`
(does it use `wmma`/`mma`?) and the `stage4_performance/.../benchmark.json`
(`baseline_mode`, `baseline_ms`, `custom_ms`, benchmark shape) for all three.

## RESOLVED via benchmark.json (2026-07-02): the speedups are NOT trustworthy
Tensor-core markers: `matmul_fp16` + `matmul_fp32` USE wmma; the fused
`matmul_bias_gelu_fp16` does NOT (CUDA cores only). benchmark.json:
- `matmul_fp16`: custom 10.02ms vs baseline 0.647ms (cuBLAS) = 0.06× — a REAL but
  naive WMMA kernel (~4% of A100 fp16 tensor peak; achieved 10 GB/s).
- `matmul_fp32`: baseline_ms **None** (failed).
- `matmul_bias_gelu_fp16`: baseline_ms **None**; custom 0.952ms — **physically
  impossible** for a real 4096³ CUDA-core GEMM (=144 TFLOP/s > ~78 TFLOP/s fp16
  CUDA-core peak, no tensor cores) → the kernel is fast-but-wrong at the 4096²
  PERF shape (correctness only verified at ≤1024²).

Two harness problems make every GEMM speedup noise:
1. **baseline None** — `torch.compile` of a 4096² GEMM trips the 60s benchmark
   subprocess timeout (`local.py`), so the baseline intermittently fails; reported
   1.11×/0.91× came from other attempts and aren't reproducible.
2. **perf shape (4096²) >> correctness shapes (≤1024²)** — a kernel can pass the
   correctness gate yet be fast-and-wrong at the perf shape (the impossible 0.952ms).
