## What this does NOT prove

- **One kernel, one architecture.** `matmul_bias_gelu_fp16` on sm_80 only.
- **The prebuilt `.so` path is untested.** Polish was rejected on this run, so no
  `.so` existed and the JIT source build ran. The `torch.ops.load_library` branch
  and its fallback have never executed.
- **Performance was not re-measured after export.** `VERIFICATION.md` reports the
  1.25× from the original run; the exported package was checked for *correctness*,
  not for still hitting that number. An exported kernel could in principle build
  differently and be slower. Closing this needs a benchmark in the standalone check.
- **Only one exported package per process.** The op registers under the fixed
  `cuda_engine::forward` namespace, so a second package's `TORCH_LIBRARY`
  registration collides. Needs a per-package namespace before anyone ships several.
- **Shape coverage.** Checked at 256 bound to every symbolic dim, not at the
  correctness-suite shapes or the 4096² benchmark shape.

## Defects found by building and running this — four

None were reachable from the unit suite.

1. **`python -m cuda_engine.cli` silently did nothing and exited 0** — no
   `__main__` guard. The driver's first draft used it, so export would have
   "succeeded" while producing no package. Fixed; the driver now confirms the
   artifact exists rather than trusting an exit code.
2. **The exported package ignored the run's nvcc flags**, JIT-building with
   torch's defaults instead of the `-O3 --use_fast_math` the kernel was measured
   with — so the installed kernel would not have been the one `VERIFICATION.md`
   describes. Flags now travel in `manifest.json` and are used by the loader.
3. **The kernel-source candidate paths were wrong.** `codegen.py:90` writes to
   `{artifact_prefix}/final/kernel.cu`, not `stage2_codegen/kernel.cu`. Three real
   run directories were all rejected as "missing kernel.cu" while containing
   kernels. The unit tests could not catch it — the fixtures wrote to the same
   wrong paths the implementation read from, so they agreed and both were wrong.
   `_select_kernel` now reads the accepted path the run recorded in
   `checkpoint.json`, which also covers repair and escalation kernels that no
   fixed list can enumerate. (`matmul_fp32` records its kernel under
   `stage4_performance/perf_repair/attempt_01/` — unexportable without this.)
4. **`ninja` was not declared as a dependency**, so the default source-build path
   failed on first use with an opaque torch error. Now declared, and build
   failures are re-raised with what to do about them.

Defects 3 and 4 were only reachable by pointing the tool at real run directories
on real hardware. That is the argument for this harness existing.
