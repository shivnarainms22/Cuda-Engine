# GEMM v2.0 — Rung 4 Evidence: WMMA Guidance Experiment (REVERTED)

**Date:** 2026-07-20
**Branch:** `v2.0/gemm`
**Outcome:** Rung 4 (WMMA/tensor-core codegen guidance) was a **net regression** and
has been **reverted**. Rungs 1–3 are retained. This document records the full
experiment and all measured numbers so the finding is not relearned.

---

## Hypothesis

Rung 1–3 left `matmul_fp16` failing with `BudgetExhausted` — the LLM could not
compile a WMMA (tensor-core) kernel in its 3 codegen attempts. Rung 4 injected a
correct WMMA reference into the codegen system prompt (for fp16/bf16 matmul-shaped
specs only) on the theory that *compiling* WMMA was the bottleneck, and that a
correct reference would unblock fp16 GEMM.

## Pre-flight validation (credit-free)

Before spending Anthropic credits, the guidance text itself was validated on
hardware for **zero credits** (nvcc + torch on a Colab A100; the `tools/wmma_guidance_check/`
harness, since removed with the revert):

- **4 defects found and fixed** in the guidance before any paid run — each would
  have burned repair-loop budget:
  1. `matrix_b` declared `col_major` while engine inputs are row-major contiguous
     → compiles but silently computes A @ Bᵀ (fails correctness, not compile).
  2. fp32 accumulator stored directly to a `half*` output → no matching
     `store_matrix_sync` overload → **hard compile error** (the prime suspect for
     the original `BudgetExhausted`). Fixed with per-warp shared staging + `__float2half`.
  3. Remainder path described as optional; the correctness gate runs N = 1, 127,
     4097 (not multiples of 16) → a WMMA-only kernel cannot pass.
  4. (introduced while fixing #2, caught on re-read) block-shared staging buffer
     used from per-warp code → data race at blockDim > 32.
- **Positive check:** compiled at sm_80; `max_rel_err = 0` at N = 0,1,127,128,1024,4097,4096.
  (Exactly zero is expected: the input generator emits multiples of 1/8, so products
  are multiples of 1/64 and fp32 accumulation is exact → bit-identical to cuBLAS.)
- **Negative control** (`-DNEGATIVE_CONTROL`, restoring the col_major defect):
  caught it — rel err 1.5–12.9 vs rtol 0.02 at N = 127,128,1024,4097,4096; N=1
  correctly passes (1×1 matmul is layout-invariant). The harness demonstrably can
  fail → the green run is meaningful evidence.

## Credited run (A100, ~$2–6) — `gemm-rung4`

Model: `anthropic:claude-sonnet-4-6`. All baselines measured (`baseline_status=ok`);
all kernels correct at the 4096² benchmark shape (Rung 2/3 integrity intact — no
fake wins).

| Kernel | Rung 3 (before Rung 4) | Rung 4 (this run) | Δ |
|---|---|---|---|
| `matmul_bias_gelu_fp16` | **1.25× PASS** (real fused CUDA-core win) | **0.09×** PASS | 💀 lost the thesis win (−14×) |
| `matmul_fp16` | FAIL (`BudgetExhausted`, WMMA wouldn't compile) | **0.11×** PASS (compiles, correct) | compile fixed, but a perf dead end |
| `matmul_fp32` | 0.66× PASS | 0.67× PASS | unchanged (guidance correctly does not fire for fp32 — not a tensor-core dtype) |

Run-level: pass rate 3/3; median speedup 0.11×; p25 0.10×; fast_1 0/3;
`speedup_vs_reference` 0.08 / 0.09 / 0.66.

## Interpretation

- **Rung 4's stated goal succeeded:** the WMMA compile failure is fixed —
  `matmul_fp16` went `BudgetExhausted` → correct-and-passing.
- **But it destroyed the one validated GEMM win.** The 1.25× `matmul_bias_gelu_fp16`
  kernel was a **CUDA-core** fused kernel. The guidance says *"tensor cores
  recommended for throughput,"* so the model rewrote it as **naive WMMA**, which
  runs at ~10% of peak. Both fp16 kernels collapsed to the same ~0.09–0.11× floor.
- **Bare fp16 GEMM vs cuBLAS was never winnable and was never the goal** (see the
  Rung 1 design: "beating cuBLAS on bare GEMM is NOT the goal"). Rung 4 bought a
  correctness pass on an unwinnable kernel at the cost of the fused-epilogue win
  that *is* the v2.0 thesis.

## Decision: REVERT

The WMMA guidance is net-negative for the project, so it was removed:

- Removed `_WMMA_GUIDANCE`, `_tensor_core_matmul_guidance`, `_is_matmul_spec`, and
  the codegen-system-prompt injection (`src/cuda_engine/stages/codegen.py`).
- Removed the now-dead `tests/unit/test_codegen_wmma_guidance.py` and the
  `tools/wmma_guidance_check/` validation harness.
- Restores the engine to the Rung 3 state: `matmul_bias_gelu_fp16` back to its
  validated 1.25× fused win; `matmul_fp16` back to FAIL, which is the **honest**
  state — the engine's defensible GEMM value is the fused CUDA-core epilogue that
  beats torch's fused path, not limping to 0.11× against cuBLAS on bare GEMM.

Cost to revert: zero credits, no re-run needed — 1.25× is the already-validated number.

## What a future tensor-core rung would need (not attempted)

Naive WMMA at ~10% peak is a dead end. Competitive fp16 GEMM needs real WMMA
optimization — shared-memory staging with double buffering, multiple output tiles
per warp, vectorized loads, K-loop pipelining. That is a large, sophisticated lift
the current single-shot codegen + repair loop will not produce from a prompt, and
it is orthogonal to the fused-epilogue thesis that already wins. Not a priority.
