# v1.5 — Synthesis-Stage Resumability — Design

**Status:** Approved (brainstorming, 2026-06-29)
**Increment:** First sub-project of v1.5 "hardening" (sequence: resumability →
persistent run DB → autotuning sweeps; Hopper `sm_90` verification dropped — no
H100 hardware). Each sub-project gets its own spec→plan→build cycle.
**Builds on:** v1.1.0 (shipped). Branch `v1.5/resumability` off `main`.
**Hardware:** A100 / local only — no new GPU dependency.

## 1. Problem & goal

A synthesis run executes five stages sequentially (Interview → Codegen →
Correctness → Performance → Polish), each writing artifacts to the run dir. If a
run dies mid-pipeline — Colab disconnect, Anthropic credit exhaustion, a stall —
**all completed work is lost and re-paid on the next attempt.** This has cost the
project real money/time repeatedly.

**Goal:** resume a single kernel's run from the first incomplete stage, reusing
the persisted outputs of completed stages (zero LLM calls for them), without ever
silently resuming against changed inputs.

**Done =** `cuda-engine synthesize --resume <run_id>` (and
`synthesize(..., resume_run_id=...)`) re-hydrates completed stages from disk and
continues; a changed prompt/reference is detected and refused; covered by a test
that crashes mid-pipeline and proves completed stages issue zero LLM calls on
resume.

## 2. Mechanism — stage-level checkpoint + rehydrate

### 2.1 Checkpoint
- The orchestrator writes/updates **`checkpoint.json`** in the run dir after each
  stage completes. It records:
  - `inputs_fingerprint` — a hash of `prompt` + reference source + the
    resume-relevant config fields (written once at run start).
  - `completed_stages` — ordered list of stage names that finished.
  - `artifacts` — the canonical output path/locator each completed stage produced
    (spec JSON, final kernel source, correctness report JSON, performance report
    JSON), so the resume path can re-hydrate without recompute.

### 2.2 Resume entry
- CLI `cuda-engine synthesize --resume <run_id>`; library
  `synthesize(prompt, reference, ..., resume_run_id=<id>)`.
- On resume the orchestrator:
  1. Loads `checkpoint.json` from the run dir.
  2. **Validates** the recomputed `inputs_fingerprint` against the stored one.
     Mismatch → raise a clear error ("inputs changed since run <id>; cannot
     resume — start a fresh run") and do nothing destructive.
  3. Re-hydrates the in-memory `KernelSpec` / `KernelArtifact` /
     `CorrectnessReport` / `PerformanceReport` from the recorded artifacts for
     each completed stage (`model_validate` on stored JSON; read source files).
  4. Continues from the **first stage not in `completed_stages`**, running it and
     all later stages normally. Completed stages issue no LLM calls.

### 2.3 Granularity
- **Whole-stage.** An incomplete stage re-runs from its start; within-stage retry
  / Sonnet→Opus escalation / repair-loop state is NOT resumed (YAGNI — a single
  stage restart is cheap relative to the stages it skips).

### 2.4 Trigger
- **Explicit `run_id`** only (the id is already printed when a run starts).
  No auto-resume-latest (avoids silently picking up the wrong run).

## 3. Components & boundaries
- **`checkpoint.py`** (new, in the orchestrator package): a small `Checkpoint`
  model + `write_checkpoint` / `load_checkpoint` + `compute_fingerprint`. Pure
  and independently testable.
- **`Orchestrator.run`** gains an optional `resume_run_id`; the linear stage
  sequence is guarded so each stage either re-hydrates from the checkpoint or
  executes. Keep the change surgical — the default (no resume) path stays
  behavior-identical.
- **`ArtifactStore`** stays write-first but gains a minimal `read_text` /
  `read_json` (and `exists`) so resume can load prior outputs through the same
  seam instead of touching the filesystem directly.

## 4. Error handling
- Missing/corrupt `checkpoint.json` for the given run_id → clear error, no resume.
- Fingerprint mismatch → refuse (§2.2.2).
- A completed-stage artifact referenced by the checkpoint is missing on disk →
  treat that stage as incomplete and re-run from there (degrade gracefully).

## 5. Testing
- Pure unit tests for `compute_fingerprint` (stable; changes when prompt/
  reference/config change) and checkpoint round-trip.
- Orchestrator test: run with a mock LLM that raises after stage N; assert
  `checkpoint.json` lists stages 1..N-? completed; resume with a fresh mock LLM
  and assert the mock receives **zero** calls attributable to the completed
  stages while later stages execute; final result is complete.
- Fingerprint-mismatch test: resume with a different prompt → raises.
- All via mock LLM/GPU/store — no hardware.

## 6. Out of scope
- Persistent run DB; autotuning sweeps (later v1.5 sub-projects).
- Within-stage / mid-retry resumption.
- Hopper `sm_90` runtime verification (no H100).
- Auto-resume / run discovery UX.
